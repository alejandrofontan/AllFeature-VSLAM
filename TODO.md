### Likely bugs / correctness

| File | Location | Issue | State | Solution Applied |
|---|---|---|---|---|
| Image.cpp | `LoadMask`, L44 | `maskPath.substr(0, 43) + "mask" + maskPath.substr(46, 50)` assumes an exact fixed path length/layout. Throws `std::out_of_range` for any path shorter than ~96 chars, and silently builds a garbage path for any dataset laid out differently than the original developer's machine. Currently entirely dead in practice: `LoadMask` is only called from a commented-out line in `vslamlab_allfeature_mono.cpp`, and the resulting `mask` field is only referenced in a commented-out line in `Feature_surf64.cpp`. | SOLVED | Rewrote `LoadMask` to take the mask path directly and `cv::imread` it, mirroring `LoadDepth` — no more path derivation, no more crash/garbage-path risk. |
| Image.cpp | `FixImageSize`, L83 | Calls `cv::resize(grayImg, grayImg, new_size)` without checking `grayImg` was populated first. If a caller invokes `FixImageSize` before `GetGrayImage`, `cv::resize` throws on the empty source. Currently only safe because `Tracking::GrabImageMonocular` (`Tracking.cc` L79/L81) happens to call them in the right order — the class itself enforces nothing, which is a risk when wiring up a new (RGB-D) call path. | SOLVED | Added an explicit `if (grayImg.empty()) throw std::runtime_error(...)` guard at the top of `FixImageSize`, so misuse now fails with a clear message instead of an opaque `cv::Exception` deep inside `cv::resize`. |
| Image.cpp | `FixImageSize`, L80-91 | Resizes/crops `img`, `grayImg`, and (since the depth changes) `depthImg`, but never touches `mask`. If a mask were ever actually loaded, it would stay at the original resolution and go pixel-misaligned with everything else post-resize/crop. | SOLVED | Added the same conditional resize+crop treatment as `depthImg`, guarded by `!mask.empty()`. Used `cv::INTER_NEAREST` for the resize since a mask is categorical/binary — linear interpolation would blend values across boundaries, same reasoning as the depth image. |
| Image.cpp | `Image(const std::string&)`, L20-25 | `replaceAllOccurrences(keypointBinFile, "png", "bin")` (and the `scoresBinFile`/`descriptorsBinFile` equivalents) replaces *every* occurrence of `"png"` in the full path, not just the file extension — a dataset path with `"png"` in a directory name (e.g. `.../png_sequences/...`) would get corrupted beyond just the extension swap. | SOLVED | `keypointBinFile`/`scoresBinFile`/`descriptorsBinFile` and their derivation logic were removed outright (R2D2-specific bookkeeping unused outside `Image`), so this bug no longer has any code to trigger it. |
| Image.cpp | `Image(const std::string&)`, L16 | `img = cv::imread(imageFile, cv::IMREAD_UNCHANGED)` return isn't checked — a bad path leaves `img` silently empty with no log/flag from the class itself. Only caught today because the CLI entry point checks `im.img.empty()` after construction; any other caller has to know to do the same. Inconsistent with the new `LoadDepth`, which does log on failure. | SOLVED | Added an `if (img.empty())` check right after the `cv::imread` that logs to `stderr`, matching `LoadDepth`/`LoadMask`'s style. Doesn't throw — callers (e.g. the CLI entry point) still decide how to react to an empty `img`, only now the class itself also surfaces the failure. |
| Image.cpp | `LoadMask`, L43-45 | Same silent-failure gap as above — no empty check/log after `cv::imread`, unlike the new `LoadDepth`. | SOLVED | Same fix as the row above: `LoadMask` now logs to `stderr` via an `if (mask.empty())` check, matching `LoadDepth`'s style. |
